# OKX 固定区间等 U 网格开发计划

状态：设计基线，尚未接通 OKX 下单。开发分支：`feat/okx-equal-usdt-fixed-grid`。

本分支从 `ledger` 的提交 `b460a4f` 建立。原工作目录中尚未提交的调度器/配置修复及 SOL 对比脚本仍保留在原目录，不会自动出现在本分支；进入联调前需核对并移植其中与本版运行有关的修复。

## 目标与范围

在现有 `grid_trading` 服务中新增一种独立的「固定区间等 U 网格」策略，先支持做多，覆盖 OKX 现货和 USDT 保证金永续合约。保留当前 Binance 触发式移动网格的行为。新策略使用普通订单 API 自行管理订单，不调用 OKX 平台内置网格策略。

用户输入：交易所、产品（现货或 USDT 永续）、交易对、区间下界、区间上界、网格数 `N`、网格交易预算 `B`；合约默认 1 倍杠杆。手续费与资金费预留资金位于 `B` 之外。`B` 是这套策略的投入预算，不等于 OKX 账户总资产，也不等于 VIP 等级的资产门槛。

本版包含手动追加预算；不做逐格利润自动复投。合约资金费记入策略级费用与账户核对，不按格分摊，也不自动从每格预算中扣除。价格越界时区间不移动、不强制平仓、不增设新格；已存在的对偶订单继续按原价工作。

## 网格与资金口径

1. 在 `[lower, upper]` 内生成 `N` 个价格区间、`N+1` 个边界。原始公比为 `(upper / lower) ** (1 / N)`；按交易所价格精度取整后仍须严格递增，否则预览拒绝创建。
2. 每格目标投入预算为 `b = B / N`。同一格的买入数量按该格买价和 `b` 计算；实际订单数量按 `lotSz`、`minSz` 和合约面值调整。卖出数量来自该格实际持有的净数量，不能直接以卖价再除一次 `b`。
3. 启动时以交易所最新可交易价格确定买格和卖格：卖价高于该价格的格子归卖侧，其余归买侧。预览列出两侧格数、计划初始建仓名义额、各格订单数量、费用估算和取整尾差。正式启动前重新取价和重新预览；价格跨格后，用户看到的预览须更新，不能沿用旧分组直接下单。
4. 设卖格数为 `S`，初始合并买入名义额目标为 `S × b`。一次性建立初始总仓位；只把确认成交的净数量按各卖格预算比例分配到逻辑格子，再创建对应高位卖单。现货买入手续费若从基础币扣除，使用扣费后的净基础币数量。合约使用实际成交张数和面值换算。无法达到最小交易量的格子在预览阶段报错或明示无法交易，不静默抛弃。
5. 卖格完成卖出后，该格使用自己的 `b` 在低边界重新挂买单。买格成交后，以实际净持仓数量挂高边界卖单。盈利留在策略之外的可用余额中，直到用户手动追加预算。
6. 手动追加 `Δ` 时每格预算增加 `δ = Δ / N`。对当前卖格，合并增加 `S × δ` 的总仓位，把确认成交的净新增数量分配给卖格并更新卖单；对当前买格，按新的单格预算更新尚未成交的买单。部分成交格按已持仓部分与未成交余量分别处理。整个操作使用同一增资事务编号，重复请求不能重复开仓。

所有投入按实际成交金额和数量记账。交易所精度导致的不能均分部分记为策略尾差，不人为扩大任何格的预算。现货与合约的订单数量口径不同，不能共用 `quantity = USDT / price` 的裸计算。

## 核心状态与安全约束

- 每个逻辑格记录：目标预算、已占用预算、持仓数量、成本、买卖订单 ID、已成交数量、周期状态与最后一次增资事务。订单与成交事件独立落库。
- 同一策略的逻辑持仓之和必须与分配给该策略的交易所真实持仓一致，允许显式记录的精度尾差。策略卖单未成交数量之和不得超过其可卖现货数量或可平合约数量。其他策略及手工仓位不能被本策略认领。
- 启动、增资和改单按「记录意图 → 提交订单 → 以客户端订单号查询结果 → 落库实际成交 → 更新逻辑格 → 发布对偶订单」恢复。超时或未知结果先查单，禁止盲目重试开仓。
- 增资期间先锁定本策略的调度和相关格，再同步订单、成交与仓位；若已有挂单部分成交，只依据最新成交结果重算余量。改单失败时保留原单并进入可恢复状态，不能假定新数量已生效。
- 开仓或增资前校验账户模式、可用余额、最小下单量、最大在途订单数、1 倍合约杠杆、预留费用及账户现存同交易对敞口。合约平仓单使用 OKX 对应模式下的平仓语义，避免卖单反向开仓。
- 下单和续挂采用可验证的 maker 模式；`post_only` 因穿价被取消时重新取价处理，不能计作已挂单。初始合并建仓单若采用立即成交方式，其 taker 费、成交价及滑点单独展示。
- 实际成交手续费按币种记录。OKX 账户费率从 `GET /api/v5/account/trade-fee` 查询，预览用账户当时费率估算，最终以成交回报为准；VIP 等级变化不改变已经入账的手续费。

## 实施顺序

| 阶段 | 交付物 | 验收条件 |
| --- | --- | --- |
| 1. 规则与预览 | 独立的固定区间策略类型、纯等比价格/等 U 分配计算、数量取整规则、预览 API | 边界、格数、卖买侧划分和总预算恒等式正确；小预算与精度冲突明确报错 |
| 2. 状态与增资 | SQLite 迁移、逻辑持仓与成交账、幂等增资事务、重启恢复 | 初始合并建仓与手动增资各只记一次；部分成交、超时、进程重启后不重复开仓 |
| 3. OKX 接入 | 现货与 USDT 永续适配器、行情/精度/余额/费率/普通订单/成交/持仓接口 | 只读接口核对通过；模拟盘完成建仓、挂单、改单、撤单、恢复与账户对账 |
| 4. 前端 | 创建/预览、启动、暂停、手动增资预览与执行、格子/总仓位/费用/尾差展示 | 网格数支持至少 100 格；预览和实单的参数一致；用户能区分网格预算与账户资产 |
| 5. 仿真与上线验收 | 与实盘同口径的固定网格回放、费率敏感性与越界场景、OKX 模拟盘闭环 | 现货与合约的账本和状态转换一致；断线、部分成交和重复请求场景通过；真实账户只读核对后才允许小额实单 |

现有 `grid_rule` 与 `strategies_system` 的固定网格仿真可复用规则和回测组件，但不直接替换已经运行的 Binance 策略引擎。现有 `Exchange` 接口没有市价/立即成交建仓、改单、成交明细、余额或账户费率，需要扩充端口；当前 `FuturesMarket`、SQLite 约束、API 工厂和前端仅识别 Binance U 本位/币本位，也需要把交易所和产品类型分开建模。

## 开发验收场景

- `B=10,000 U, N=100`，每格目标 `100 U`；卖格为 40 时初始合并建仓目标 `4,000 U`、买格预算合计 `6,000 U`。
- 追加 `Δ=1,000 U` 时每格增加 `10 U`；卖侧合并追加 `400 U`，买侧预算合计增加 `600 U`。实际成交数量和取整尾差可追溯。
- 当前价恰好落在网格边界、区间外、增资时价格跨格、一个卖单部分成交、初始合并单部分成交、改单失败、请求超时和重启恢复均有确定行为。
- 账户同交易对存在手工仓位或另一策略时，不能把它们分配给本策略；运行中的 Binance 网格行为保持原样。
- 预览按账户实际费率计算往返成本。公开 VIP1 通用费率仅作为示例：现货 maker 0.0675% / taker 0.0800%，永续 maker 0.0160% / taker 0.0450%；资金费和滑点单独列示。
