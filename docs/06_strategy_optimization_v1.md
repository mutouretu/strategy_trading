## 2. 模块定位

第六部分回答：

> 在明确的策略思想、账户模型、执行成本和市场范围内，哪些规则与参数能够在
> 收益、风险和稳定性之间形成更好的可解释组合？

它不是 simulator 的新执行功能，也不是新的交易规则引擎。它主要建立一套可复现的
研究工作流：

```text
研究假设或参数空间
        ↓
StudySpec
        ↓ 编译
ExperimentSpec
        ↓
现有 experiment_system
        ↓
simulation_runtime + strategy_simulation
        ↓
现有指标与 SQLite 结果
        ↓
敏感性分析 / 稳定区域 / Pareto 候选
```

第六部分会增加少量研究编排、候选筛选和结果展示代码，但不会改变已经确定的核心
调用关系。

## 3. v1.0 目标

第六部分 v1.0 的目标是：

1. 固定一套基线和可比较的评估协议；
2. 为同一策略建立可复现的人工规则变体实验；
3. 使用现有参数轴完成粗扫、细扫和敏感性分析；
4. 在多个市场窗口和成本假设下识别稳定参数区域；
5. 使用硬约束和 Pareto 前沿筛选候选，而不是直接给出一个不透明总分；
6. 将 Study、候选、筛选理由和实验结果保存在统一 SQLite 中；
7. 在现有前端中展示基线、参数分布、Pareto 前沿和候选详情；
8. 为以后动态参数控制和强化学习预留明确接口，但不将其作为 v1.0 验收前提。

v1.0 的产物不是“保证盈利的最优策略”，而是：

```text
在什么数据、账户和费用条件下，
哪个策略版本的哪些参数范围表现相对稳定，
它相对基线获得了什么，承担了什么风险，
又在哪些环境下会失效。
```

## 4. 设计原则

### 4.1 先有基线，再谈优化

任何优化 Study 必须声明基线。没有基线的最高收益没有研究意义。

首批基线至少包括：

- 持有 1.1 BTC、不交易；
- 目标强平价阶梯止盈；
- 单组跟随网格；
- 分层跟随网格。

其中“持有 BTC”是绝对基线，其余是同一账户与市场条件下的策略基线。

### 4.2 机制分析优先于黑箱搜索

先提出可解释假设，例如：

- 网格过密时，手续费是否吞噬毛收益；
- 网格过宽时，成交频率是否不足；
- 跟随复位是否在趋势行情中反复损失库存；
- 分层是否提高了震荡收益，却放大了单边下跌敞口；
- 固定单格仓位是否造成高位和低位资本配置不合理。

每个规则改进先形成独立策略版本和对照实验，再进入大规模参数搜索。

### 4.3 重计算，轻结论

仿真和指标系统继续只计算事实。第六部分可以定义研究约束和候选筛选，但不得：

- 修改 Fill、账本、保证金或强平结果；
- 在指标公式中暗藏策略排名；
- 将研究偏好写入 `simulation_runtime`；
- 为了保留候选而覆盖原始实验事实。

### 4.4 不同计价目标不得混排

COIN-M BTC 积累策略和 USDⓈ-M 收益策略必须使用不同的目标配置：

```text
coinm-btc-accumulation/v1
    以 BTC 权益和相对 HODL 的超额 BTC 为主目标

linear-usdt-return/v1
    以 USDT 权益和 USDT 收益率为主目标
```

两种策略可以在同一系统中研究，但不得把各自的“收益率”直接放在同一排行榜中。

### 4.5 寻找稳定区域，不追逐单点最高值

参数搜索重点回答：

- 相邻参数是否表现接近；
- 更换时间窗口后是否仍有效；
- 手续费、资金费和滑点假设稍变后是否立即失效；
- 最差窗口和低分位结果是否可接受。

孤立的最高点默认视为过拟合嫌疑，而不是最终候选。

### 4.6 最终样本外数据保持隔离

研究数据按时间顺序划分，不做随机打乱：

```text
训练区间
    用于规则分析和参数搜索

验证区间
    用于选择稳定区域和 Pareto 候选

最终样本外区间
    第六部分结束前保持锁定，由第七部分正式验证
```

第六部分可以反复使用训练集和验证集，但不得根据最终样本外结果继续调参。

### 4.7 每个结论都必须可复现

每个 Study 必须记录：

- 策略类型、策略版本和参数指纹；
- 市场数据标识、时间范围、周期和内容指纹；
- 账户、杠杆、保证金和费用配置；
- 资金费假设；
- Seed；
- 代码提交；
- 指标公式版本；
- Study 约束、目标和选择理由。

### 4.8 与第七部分的边界

第六部分需要使用训练集和验证集比较候选，这是优化过程内部的研究验证；第七部分
负责对已经锁定的候选执行正式验证：

```text
第 6 部分
    改规则、扫参数、比较训练/验证窗口、锁定候选

第 7 部分
    不再调参，运行最终样本外、独立历史复验和实盘适用性评估
```

如果第七部分失败，候选可以退回第六部分重新研究，但必须形成新的策略或参数版本，
并更换新的最终样本外验证范围，不能在看过失败样本后继续沿用原“未见数据”标签。

## 5. 代码归属与依赖边界

### 5.1 工程归属

第六部分继续放在 `strategies_system`，不新建仓库。

建议增加第三个 Python 包 `strategy_optimization`：

```text
strategies_system/
├── src/
│   ├── trading_strategies/          # 纯策略核心
│   ├── strategy_simulation/         # 仿真 Adapter、Plugin、Provider
│   └── strategy_optimization/       # Study、搜索、筛选和研究结果接口
├── experiments/                     # 可直接执行的固定实验规格
├── research/
│   ├── protocols/                   # 评估协议与数据划分
│   ├── parameter_search/            # 参数空间和 Study 输入
│   ├── scenario_studies/            # 市场与成本敏感性 Study
│   ├── optimization/                # Pareto 与候选选择定义
│   ├── model_training/              # 动态模型/RL，后期启用
│   └── reports/                     # 按需生成的研究报告
└── tests/
```

`research/` 保存版本化研究输入和少量报告，不保存散落的 Run JSON。Run、Trace、
指标和候选状态继续以 SQLite 为正式结果来源。

### 5.2 三个 Python 包的责任

```text
trading_strategies
    决定何时建仓、建多少、使用什么规则、何时复位或退出

strategy_simulation
    把纯策略接到 simulation_runtime 和 experiment_system

strategy_optimization
    定义研究问题、展开候选、读取指标、筛选和比较结果
```

依赖方向为：

```text
strategy_optimization
        → experiment_system 公共接口
        → metric_system / result_repository 公共接口
        → strategy_simulation 的 Provider 注册入口

strategy_simulation
        → trading_strategies

trading_strategies
        不依赖 strategy_simulation、strategy_optimization 或 market_simulator
```

`strategy_optimization` 不得生成 `TradeInstruction`，不得直接操作账本，也不得成为
实盘 Server 的运行时依赖。

### 5.3 不新建第二套实验系统

Study 只比现有 Experiment 多一层研究语义：

```text
StudySpec
    研究目标、基线、数据划分、参数空间、约束和选择规则

ExperimentSpec
    市场 × 策略 × 执行 × 账户 × 参数轴 × Seed 的实际运行计划
```

`StudyCompiler` 将 Study 编译为一个或多个现有 `ExperimentSpec`。实际展开、运行、
失败恢复、结果保存和 Trace 保留仍全部由第二部分的实验系统负责。

### 5.4 通用能力的归属

第六部分先在 `strategies_system` 中实现。只有当某项能力已经证明与策略领域无关，
且其他研究项目也需要复用时，才考虑以后下沉到 `market_simulator`。

v1.0 不提前建设通用分布式调度器、独立优化服务或新的数据库服务。

## 6. Study 模型

### 6.1 StudySpec 最小字段

建议的研究定义如下：

```json
{
  "schema_version": "strategy-study/v1",
  "study_id": "coinm-single-following-grid-v1",
  "strategy_family": "single-following-grid/v1",
  "objective_profile": "coinm-btc-accumulation/v1",
  "baseline_ids": [
    "hold-btc/v1",
    "single-following-grid-baseline/v1"
  ],
  "dataset_split_id": "btc-coinm-history-split-v1",
  "execution_profile_ids": ["binance-coinm-maker-v1"],
  "account_profile_ids": ["coinm-cross-1.1btc-v1"],
  "parameter_space": [],
  "eligibility_constraints": [],
  "objectives": [],
  "selection_policy": "pareto-robust-region/v1"
}
```

具体数值继续使用字符串保存 Decimal。Study 中只保存引用和研究语义，组件实际结构
仍由 `ExperimentSpec` 和 Provider 校验。

### 6.2 Study 状态

Study 至少具有以下状态：

```text
DRAFT
    研究定义可修改，尚未形成正式结论

PLANNED
    参数组合和 Run 数已经展开并确认

RUNNING
    部分或全部 Run 正在执行

EXECUTED
    Run 已结束，尚未完成目标与候选评价

EVALUATED
    指标已完成，尚未锁定候选

SELECTED
    已保存候选和选择理由

INVALIDATED
    数据、代码或指标变化导致旧结论失效
```

Study 状态只描述研究过程，不改变子 Run 的原始状态。

### 6.3 结果保存

v1.0 原则为“一项 Study、一个正式 SQLite 结果库”：

- Experiment、Run、Summary、Trace 和 Metric 使用现有表；
- Study 定义、参数候选、Pareto 成员、人工选择和选择理由使用
  `strategy_optimization` 自有表；
- 报告和 CSV 只按需导出，不是正式数据源；
- 候选可标记为 `shortlisted` 或 `archived`，但不得删除失败和被淘汰的事实记录；
- 删除整个 Study 时走现有显式删除流程，不留下指向已删除 Run 的孤立索引。

完整优化阶段预计使用：

```text
optimization_studies
optimization_candidates
optimization_objectives
optimization_selections
```

6A 只实现已经具有确定语义的：

```text
optimization_studies
optimization_study_events
```

候选、目标评价和人工选择表分别在 6D、6F 确定查询与幂等语义后增加，避免先建一组
没有稳定含义的空表。

是否必须修改通用 SQLite schema，在 6A 先通过现有扩展机制验证；如可由策略工程在
同一数据库中维护命名空间表，则不修改 `market_simulator` 核心仓储。

## 7. 统一评估协议

### 7.1 COIN-M BTC 积累目标

首个正式目标配置使用 `coinm-btc-accumulation/v1`。

主指标为：

```text
final_equity_btc
excess_btc_vs_hodl
excess_btc_rate_vs_hodl
```

其中：

```text
excess_btc_vs_hodl
    = 策略期末 BTC 权益 - 同市场同初始资产 HODL 期末 BTC 权益

excess_btc_rate_vs_hodl
    = excess_btc_vs_hodl / HODL 期末 BTC 权益
```

USDT 权益仍要展示，用于观察法币计价结果，但不得把 BTC 价格自然上涨误认为策略
产生的 BTC 收益。

### 7.2 USDⓈ-M 收益目标

U 本位策略使用 `linear-usdt-return/v1`，主指标为：

```text
final_equity_usdt
total_return_usdt
net_profit_usdt
```

近期 50,000—80,000 区间、固定 USDT 下单量的真实行情网格实验属于该目标配置，
可用于验证成交频率和手续费影响，但不作为 COIN-M BTC 积累策略的直接收益基线。

### 7.3 风险指标

两类目标都至少检查：

- 是否强平和强平率；
- 最大回撤；
- 最低保证金安全余量或最接近强平程度；
- 最大名义敞口；
- 最大持仓；
- 期末未退出仓位；
- 最坏窗口结果；
- 低分位结果。

强平是账户执行事实，不是策略风控规则。优化层只能把它作为约束或目标读取。

### 7.4 成交和成本指标

至少保留：

- Fill 数；
- 完成循环数；
- 买卖方向分布；
- 毛交易收益；
- 手续费；
- 资金费；
- 净交易收益；
- 单循环平均净收益；
- 手续费 / 毛交易收益；
- 时间在场比例和资金占用。

成交数是策略行为指标，不是越高越好的收益目标。PI 网成交频率复现实验继续作为
执行与参数校准样例，不直接决定策略优劣。

### 7.5 硬约束与优化目标分离

每项 Study 应分别声明：

```text
Eligibility Constraints
    候选是否有资格进入比较

Objectives
    有资格候选之间如何形成 Pareto 前沿
```

默认建议的资格条件为：

- 实验正常完成；
- 指标完整且公式版本一致；
- 未强平；
- 不存在非法账户状态；
- 期末状态能够解释。

最大回撤、最低保证金余量等阈值由具体 Study 配置，不在框架中写死。

## 8. 市场数据与样本划分

### 8.1 数据层级

第六部分按用途使用三类数据：

```text
确定性小样本
    验证规则改动和边界路径

真实历史行情
    参数研究和主要候选比较

生成行情与压力场景
    扩展路径覆盖，检查策略失效方式
```

真实历史数据是首批优化的主要依据；生成行情用于补充，不用于替代真实历史事实。

### 8.2 合约和行情必须显式对应

COIN-M 基线优先使用真实 `BTCUSD_PERP` 行情。使用 `BTCUSDT` 作为价格代理时，
必须在 Study 中标记 `proxy_market=true`，不得静默视为同一市场。

USDⓈ-M 策略使用 `BTCUSDT` 对应行情和线性合约账户模型。

### 8.3 K 线周期

密集被动网格的成交频率研究优先使用 1 分钟 K 线。日线或小时线可以用于长期权益
趋势观察，但不能可靠还原 0.15%—0.55% 密集网格的日内多次循环。

每个 Study 必须记录：

- 原始周期；
- 是否经过聚合；
- 同一 K 线内多价格触发的执行假设；
- 数据缺口；
- 市场数据指纹。

### 8.4 时间划分

初始建议按连续时间块划分：

```text
60% 训练
20% 验证
20% 最终样本外
```

实际比例可根据数据长度调整，但必须满足：

- 不随机打乱时间顺序；
- 至少覆盖震荡、上涨和下跌中的两类环境；
- 最终样本外区间在候选锁定前不可用于调参；
- 所有候选使用相同时间边界。

单个 120 日行情不足以覆盖完整市场周期时，它只作为一个历史窗口，不得被描述为
长期稳定性结论。

### 8.5 成本场景

首批成本配置至少包括：

```text
基准手续费
    使用目标交易场所和账户等级的 Maker/Taker 费率

零资金费
    隔离网格规则本身的结果

历史或固定资金费敏感性
    检查资金费对长期持仓的影响

费用压力场景
    手续费或资金费略高于基准
```

在生成行情中不强行预测多空比。资金费先使用明确的外生假设；市场情绪与资金费联合
生成留到后期精细化研究。

## 9. 基线设计

### 9.1 基线账户

COIN-M 首批基线建议固定：

- 初始总资产 1.1 BTC；
- 全仓账户；
- 相同合约面值、价格精度和数量精度；
- 相同杠杆和保证金模型；
- 相同 Maker/Taker 手续费；
- 相同资金费配置；
- 相同市场窗口。

目标强平价 20,000、网格范围、单格张数等属于具体策略配置，不写入平台基线框架。

### 9.2 基线策略

首批对照矩阵为：

```text
hold-btc/v1
    不交易，回答持币本身的结果

target-liquidation-ladder-long/v1
    一次性建仓和分批止盈的简单主动策略

single-following-grid/v1
    单组跟随网格基线

layered-following-grid/v1
    多层跟随和复位基线
```

四个策略必须在同一 Market、Account、Execution 和时间范围下运行。若某策略无法使用
完全相同的账户参数，差异必须作为显式维度展示。

### 9.3 基线输出

基线报告至少回答：

- 相对 HODL 增加或减少了多少 BTC；
- USDT 计价权益变化中有多少来自 BTC 价格变化；
- 是否强平，最接近强平时的安全余量；
- 最大回撤和最大敞口；
- 成交、循环、手续费和资金费；
- 期末剩余仓位；
- 各市场窗口下的最差结果。

### 9.4 基线冻结

基线配置确认后生成不可变版本，例如：

```text
coinm-btc-baseline/v1
```

参数或数据改变必须形成 v2，不得覆盖 v1 后继续沿用旧结论。

## 10. 人工规则改进

### 10.1 研究单位

一个人工规则改进应形成：

```text
问题描述
    ↓
机制假设
    ↓
独立策略版本或显式配置开关
    ↓
确定性路径测试
    ↓
与基线相同条件的实验
    ↓
接受、拒绝或继续研究的结论
```

不得直接修改现有基线版本后重新运行。

### 10.2 首批候选问题

单组和分层跟随网格可优先研究：

- 网格跟随触发时机；
- 复位条件和复位缓冲；
- 下位网格触碰上位网格后的仓位处理；
- 最大层数；
- 新增层之间的价格距离；
- 高敞口时是否暂停新增层；
- 固定单格张数与按资本预算下单；
- 未完成循环的期末库存；
- 趋势行情中减少无效反复复位的方法。

具体规则由研究假设决定，不在本计划中提前写死。

### 10.3 版本约束

会改变状态机或交易意图语义的改动必须增加策略版本。只改变数值参数且语义不变时，
继续使用同一策略类型，通过参数指纹区分。

## 11. 参数扫描与敏感性分析

### 11.1 参数类型

网格策略常见参数包括：

- 网格等比间距；
- 网格数量；
- 单格合约张数或资本预算；
- 网格上下界；
- 跟随阈值；
- 分层间距；
- 最大层数；
- 复位缓冲；
- 暂停新增层阈值；
- 止盈或退出配置。

COIN-M 使用合约张数或 BTC 风险预算；USDⓈ-M 可以使用固定 USDT 名义金额。两者的
数量参数不得共用含糊的 `order_size` 字段。

### 11.2 分阶段扫描

不一次性对所有参数做完整笛卡尔积。建议顺序为：

```text
第一层：单参数敏感性
    确认方向、异常边界和大致有效范围

第二层：少数关键参数粗网格
    找到连续稳定区域

第三层：稳定区域局部细扫
    检查邻域是否平滑

第四层：跨市场和成本复验
    排除只适用于单一窗口的参数
```

### 11.3 搜索方法优先级

v1.0 优先级为：

1. 人工指定参数轴；
2. 笛卡尔积粗扫与局部细扫；
3. 随机搜索，仅在维度明显增加后使用；
4. 贝叶斯优化，仅在单次实验昂贵且搜索空间已经稳定后考虑。

参数扫描直接复用第二部分已有 `parameter_axes`、多市场和多 Seed 展开能力。

### 11.4 防止无效组合爆炸

`StudyPlanner` 在运行前必须显示：

- 参数候选数量；
- 市场窗口数量；
- 账户和执行配置数量；
- Seed 数；
- 总 Run 数；
- 预计 K 线处理量；
- 重复参数指纹数量。

超过 `max_runs` 必须显式确认或缩小范围。非法参数组合在运行前拒绝，不占用实验 Run。

### 11.5 敏感性输出

每个关键参数至少输出：

- 参数值与主目标的关系；
- 参数值与最大回撤的关系；
- 参数值与手续费、成交数的关系；
- 相邻参数结果变化；
- 跨窗口中位数、低分位和最差值；
- 稳定区间而不是只有最佳点。

## 12. 多目标筛选

### 12.1 默认目标

COIN-M BTC 积累首批建议使用：

```text
最大化
    excess_btc_rate_vs_hodl

最小化
    max_drawdown_rate_btc
    max_exposure
    fee_and_funding_cost

检查但不盲目最大化
    completed_cycles
    fill_count
```

具体指标键以第三部分注册表为准。Study 在运行前校验指标是否存在、单位是否一致、
公式版本是否可比较。

### 12.2 Pareto 前沿

v1.0 不提供默认综合评分。筛选顺序为：

```text
移除不满足硬约束的候选
        ↓
按验证窗口聚合
        ↓
计算 Pareto 前沿
        ↓
检查邻域稳定性和最差窗口
        ↓
由研究者保存少量候选及理由
```

人工选择必须保存：

- 选择时间；
- 候选参数指纹；
- 所属 Pareto 版本；
- 选择理由；
- 已知失效环境；
- 是否进入第七部分验证。

### 12.3 不可比较结果

以下结果不得进入同一个 Pareto 计算：

- 目标计价资产不同；
- Metric formula version 不同；
- 市场窗口集合不同；
- 初始资本不同且未归一化；
- 账户或执行成本不属于同一比较协议；
- 数据缺失或部分 Run 尚未完成。

## 13. 动态参数控制

### 13.1 定位

动态参数控制只在静态参数已经形成稳定基线后开始。它属于策略核心的决策能力，
不是 simulator 根据市场状态自动改参数。

调用关系仍为：

```text
Strategy Core
    读取截至当前时刻的市场与账户状态
        ↓
    计算当前控制状态
        ↓
    选择网格间距、仓位预算、层数或暂停状态
        ↓
    GridRule / RSI Rule 等产生机械交易规则
```

### 13.2 首批动态输入

可以研究：

- 只使用历史数据计算的实现波动率；
- 趋势强度；
- 当前仓位和名义敞口；
- 保证金安全余量；
- 最近成交频率和费用占比；
- 当前网格库存和未完成循环。

禁止使用当前时点之后的数据，特征必须记录计算窗口和延迟。

### 13.3 验收前提

动态策略必须显著优于同等复杂度的静态基线，并在多个验证窗口保持优势。否则保留
静态策略，避免为了动态而动态。

动态参数控制属于第六部分后续批次，不是 v1.0 必须交付项。

## 14. 强化学习

### 14.1 启动条件

只有同时满足以下条件才启动 RL：

1. 问题确实是连续状态下的序贯决策，而不是几个静态参数；
2. 静态扫描和人工动态规则已经形成可靠基线；
3. 市场环境足够多样，不会只记住少数历史路径；
4. Reward 可以由现有指标和账户事实明确构造；
5. 可以保留完全独立的样本外环境；
6. 推理结果仍能转换为现有策略端口和交易意图。

### 14.2 可能的状态和动作

```text
State
    市场特征、仓位、保证金、网格库存、费用和策略状态

Action
    新增层、复位层、暂停、恢复、调整间距、调整仓位预算

Reward
    BTC 或 USDT 主目标
    - 回撤惩罚
    - 强平惩罚
    - 过高敞口和费用惩罚
```

RL 环境不得另写成交、记账和强平逻辑，仍调用 `simulation_runtime`。

### 14.3 v1.0 边界

v1.0 只保留接口和数据边界，不实现训练框架，不承诺 RL 产物。

### 16.7 6G：动态参数控制（可选）

- 定义不使用未来数据的市场和账户特征；
- 实现一个最小动态控制策略；
- 与最接近的静态策略做复杂度公平的对照；
- 检查不同窗口下是否持续改善。

未证明明显价值时，不继续增加动态复杂度。

### 16.8 6H：强化学习（可选）

只有满足第 14.1 节启动条件后才制定独立方案。第六部分 v1.0 不以 6H 完成为
验收条件。

## 17. 测试计划

### 17.1 Study 单元测试

- schema 和 Decimal 字段校验；
- 参数路径和候选类型校验；
- 参数指纹确定性；
- 重复候选去重；
- 非法组合提前拒绝；
- Run 数和 K 线处理量估算；
- Study 状态迁移；
- 选择记录不可覆盖原始事实。

### 17.2 指标和目标测试

- HODL BTC 基线手算；
- 相对 HODL 的 BTC 超额收益手算；
- BTC 与 USDT 目标配置隔离；
- 强平候选的资格过滤；
- 缺失或不同公式版本指标拒绝比较；
- Pareto 支配、相等和 Decimal 边界；
- 跨窗口低分位和最差值聚合。

### 17.3 数据泄漏测试

- 时间切分严格有序且不重叠；
- 最终样本外数据不可由训练 Study 引用；
- 动态特征只读取当前及历史帧；
- 数据指纹变化后旧 Study 标记失效；
- 代理市场必须显式标记。

### 17.4 集成测试

- Study 编译为现有 ExperimentSpec；
- 参数轴、多市场、多 Seed 正确展开；
- 运行、指标计算、Study 筛选和 Viewer 贯通；
- 部分 Run 失败后可继续并正确显示；
- Trace 未保留时仍可依赖 Summary 和 Metric 完成筛选；
- 入选候选可进入现有实验详情和 K 线播放。

### 17.5 架构测试

- `trading_strategies` 不导入 `strategy_optimization`；
- `strategy_optimization` 不创建 Fill 或修改账本；
- `market_simulator` 不硬编码具体策略或参数空间；
- 实盘 Server 不依赖优化包；
- 新增参数研究不要求修改通用 Provider；
- 第六部分不复制实验运行、指标或保证金公式。

## 18. v1.0 验收标准

第六部分 v1.0 完成必须同时满足：

1. `strategies_system` 内存在独立、边界清晰的 `strategy_optimization` 包；
2. Study 能编译和调用现有 Experiment，而不是另写运行器；
3. COIN-M BTC 目标与 USDⓈ-M USDT 目标完全隔离；
4. 已固定 1.1 BTC 账户下的 HODL 和至少三类策略基线；
5. 已在真实 COIN-M 行情上完成正式基线；
6. 已完成至少一项人工规则改进的完整对照；
7. 已对至少两个关键参数完成粗扫和局部细扫；
8. 已在多个市场窗口与成本场景下检查稳定性；
9. 已实现硬约束与 Pareto 筛选；
10. 所有候选可追溯到数据、代码、配置和指标版本；
11. 最终样本外数据没有参与调参；
12. Study、候选和选择理由保存在正式 SQLite 中；
13. 前端能够查看 Study、基线、敏感性、Pareto 和候选详情；
14. 至少有 1—3 个候选可移交第七部分正式验证；
15. 三个既有模块的执行、实验和指标回归测试继续通过；
16. 动态参数控制和强化学习未完成不影响 v1.0 验收。

## 19. v1.0 暂不支持

- 自动连接实盘并部署入选策略；
- 自动把历史最优参数写回实盘配置；
- 分布式集群搜索；
- 独立数据库服务；
- 默认全局综合评分；
- 不同计价资产策略的统一收益排行榜；

- 资金费预测模型；
- 高频订单簿级别撮合优化；
- 将强化学习作为简单参数扫描的替代；
- 未经第七部分验证直接宣布策略可实盘使用。
