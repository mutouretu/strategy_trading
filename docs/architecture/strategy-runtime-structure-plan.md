# Strategy Runtime 结构调整方案与开发计划

状态：待实施

开发分支：`feat/strategy-runtime-structure`

基线：实盘版 `grid-live-v1.0.0`（`0111a36`）与 `feat/grid-rule-parity` 的合并提交 `c3bbd84`

日期：2026-11-18

## 1. 目标

让同一个 `StrategyDefinition` 和同一组 `TradingRule` 同时驱动仿真与实盘。Rule 决定网格单元格如何响应市场、成交和账户事实；运行层执行意图、维护订单和账本。已有初始建仓、阶梯止盈 Rule 与固定区间等 U 网格遵守同一套组合和事件契约。

这次调整保持现有策略的 ID、历史累计收益、运行起点和可查询的订单记录。结构调整本身不修改正在运行的 Binance、OKX 策略配置，也不要求重建仓位或撤掉交易所挂单。实盘切换单独作为最后阶段实施。

## 2. 已有基础和当前缺口

| 部分 | 当前情况 | 需要补足 |
| --- | --- | --- |
| Rule / Strategy | `strategies_system` 已有 `TradingRule → StrategyDefinition → StrategyApplication`，初始建仓、阶梯止盈和固定等 U 网格均已注册 | 固定网格 Rule 仍反向依赖 `grid_trading/grid_rule` 的纯函数；实盘未通过 Rule 实例决策 |
| 仿真 | `StrategyApplicationSimulationAdapter` 是通用桥梁；`FixedGridEventRouter` 处理网格事实 | 路由器接口定义在仿真包内，无法由实盘复用；分钟 K 线与实盘逐笔成交的可比边界需固定 |
| 实盘 | `FixedGridEngine` 已有 Binance/OKX 下单、窗口、价格带、恢复、资金与复投功能 | 它和基类 `TradingEngine` 仍混合网格决策、交易所执行和状态持久化 |
| 账本 | SQLite 按单元格统计配对净利；手续费齐备后按周期入账，复投有防重复事务 | 研究侧尚无与实盘一致的费用事实、单元格预算变更和重启恢复契约 |
| 迁移 | 实盘已有同策略重配与历史累计保留的路径 | 新 Rule 状态、旧单元格代际和进行中订单需要明确的版本化映射 |

`grid-rule-parity` 已共用价格几何、触发条件和窗口选择等纯函数，但仍有两条驱动链：仿真调用注册 Rule，实盘引擎直接调用纯函数。这是本分支要消除的核心重复决策点。

## 3. 目标边界

```text
StrategyDefinition ──组合──> InitialEntryRule / FixedGridRule / ReinvestRule / 其他 Rule
        │                                │
        ▼                                ▼
StrategyApplication <──标准化事实── 事件路由器（策略专用）
        │                                ▲
        └──交易/撤单/预算意图─────────────┤
                                         │
                       通用运行协调器（意图状态、幂等、恢复、对账）
                          ├── 仿真执行适配：K 线、成交模型、可配置费用
                          └── 实盘执行适配：Binance / OKX、真实成交与费用
```

- **Rule**：只消费明确定义的输入和自身状态，输出下一状态及意图。固定网格 Rule 负责价格几何、触发、单元格买卖配对、目标挂单窗口和按单元格预算计算目标数量。初始建仓继续由独立 Rule 负责。复投作为独立 Rule 或独立策略内政策组件，接收已核实的单元格净利、复投比例、交易精度和当前预算，输出预算增量；最终形式须符合现有 `TradingRule` 契约。
- **StrategyDefinition / StrategyApplication**：解析配置并组合 Rule，管理策略实例、意图所有权和虚拟持仓。策略级历史累计与当前单元格代际分开。原始交易所账户仓位仍由实盘对账确定。
- **事件路由器**：属于具体策略，负责把标准化的市场、订单和成交事实映射为 Rule 输入。固定网格路由器可以认识 Cell；通用协调器和通用适配器不能出现 `grid` 字段、函数名或类型分支。
- **运行协调器**：保存意图与真实订单的映射、处理部分成交和撤单、重启恢复、幂等提交、资产预留及交易所对账。它不自行决定下一格的买卖价格或目标窗口。
- **执行适配器**：Binance、OKX 与仿真分别实现成交、过滤器、价格带及账户事实接口。手续费和资金费作为账本事实进入运行层；仿真可以配置零费用。Rule 不直接调用 REST、SQLite 或 Streamlit。

目标代码边界：`strategies_system/src/trading_strategies` 保留 Rule、纯网格计算及 Strategy 定义；`strategy_application` 保存通用实例和事件/意图契约；新增顶层 `live_trading/` 承接通用实盘协调器及交易所适配器。现有 `grid_trading/` 在迁移期保留前端、API、旧引擎和兼容入口，确认切换后再逐步瘦身。`market_simulator/` 和 `strategy_simulation/` 继续负责仿真执行。`trading_ledger/` 不纳入本次迁移。

依赖方向必须从运行适配器指向 Strategy/Rule 契约；`trading_strategies` 不依赖 `grid_trading`、`live_trading`、交易所 SDK 或仿真运行时。对现有 `grid_rule` 的调用先以兼容导入保留，实盘切换通过验证后再删除旧路径。

## 4. 分阶段实施

### S0：冻结行为基线

1. 记录 `0111a36` 的固定网格行为案例：预建仓与触发式、Binance 与 OKX、窗口缺口补单、价格带等待、部分成交、重启恢复、同策略重配和复投。
2. 为案例保存确定性的输入事实、意图、订单生命周期和单元格结果；实盘敏感信息不得进入夹具。
3. 列出当前不能等价回放的现象（如分钟线内先后、盘口排队、实时价格带），避免把模拟收益相等当成验收条件。

**交付/门槛**：现有测试及基线回放通过；每种关键行为都有可重复的预期输出。

### S1：归位网格 Rule 和策略组合

1. 把固定网格几何、触发与窗口纯函数移到 `trading_strategies` 下，取消 Rule 对 `grid_trading` 的反向依赖；旧模块只做代理以维持兼容。
2. 补全 Rule 观测中的每格当前预算及目标数量，使已复投的单元格不再使用创建时的固定预算。明确单元格代际、买卖配对、`reduce_only` 和数量取整语义。
3. 让种子建仓、网格循环与复投政策在 `StrategyDefinition` 中显式组合；定义同一事件触发多条 Rule 时的协调顺序和资金限制。

**交付/门槛**：Rule 的纯函数和策略组合测试通过；入口、窗口、数量和重配前后代际在现有实盘基线案例中产生相同目标意图。

### S2：建立共享事实与通用运行契约

1. 在 `strategy_application` 附近定义与执行环境无关的市场、订单状态、成交、手续费、账户和预算变动事实，以及稳定意图标识。将通用事件路由器契约从 `strategy_simulation` 移出。
2. 仿真与实盘各自把原始事件归一化；网格路由器把标准事实映射为 Rule 输入。通用运行协调器只处理意图的发送、确认、部分成交、取消、拒单和未知结果。
3. 定义同一价格上 `entry/exit` 的顺序、批量成交边界与事件去重方式；不会因一次行情刷新重复开单。

**交付/门槛**：通用模块没有网格专用分支；同一事实流进入同一 Strategy/Rule 后生成相同意图序列。

### S3：账本、复投和持久化

1. 保留真实成交与真实手续费为实盘净利的权威数据。每格买卖配对净利在手续费完整后入账；资金费仍按账户/策略记录，不摊到单格复投。
2. 复投保持每格独立：按策略配置比例累积可用净利，跨过该标的最小数量增投门槛后，在下一轮买单中增加数量；已消费盈利、剩余未消费盈利与预算变更同事务持久化。未分配利润留在账户资金池。
3. 对 Rule 状态、意图与订单映射、每格代际和策略累计数据建立版本化快照/事件恢复。重配时保留策略 ID、运行时间与历史累计利润；新单元格从零统计，旧单元格归档，不参与新窗口决策。
4. 设计迁移程序及只读预演；验证旧 SQLite 中的进行中订单、部分成交、仓位和净利可恢复，且重复执行迁移不重复记账或下单。

**交付/门槛**：单元格净利、策略累计净利与账户差额可解释；相同事件重放、进程重启和迁移重试不会重复复投、重复建仓或丢失历史累计。

### S4：仿真与实盘一致性验证

1. 用同一组标准事实分别驱动仿真适配器和实盘适配器的离线假交易所，比较 Rule 意图、单元格状态和预算变动。
2. 再用历史 SOXL 分钟线跑策略实验；明确仿真成交模型、费用参数及样本区间。分钟线只验证在该模型下的行为，不能证明实际成交率、资金费或净收益。
3. 覆盖预建仓/触发式、0.5% 等比网格、无回踩、快速下杀、跨多格跳价、部分成交、平台撤单后补单、价格带限制、重启、双交易所和重配。

**交付/门槛**：标准化事实回放的决策完全一致；账本差异只来自显式指定的费用/成交模型，且每项差异可定位。

### S5：实盘接线与切换

1. 先在独立数据库和 Binance 测试网验证新运行链的下单、成交、撤单、补单、恢复与复投；OKX 使用模拟盘或离线假交易所补齐适配验证。
2. 实盘先运行只读影子模式：读取交易所与旧数据库事实，只计算和记录目标意图，不发送订单。比较旧引擎的真实决策，修正所有不一致。
3. 按交易所逐个切换：停止该交易所旧调度器及 API，做 SQLite 一致性备份，运行迁移预演与迁移，启动新调度器，核对策略状态、仓位、挂单、意图映射、心跳和巡检。保留已有交易所挂单，仅由一个调度器接管同一账户/策略。
4. 若核对失败，停止新调度器，使用备份和旧版本恢复；回滚步骤必须记录切换期间实际成交，不能直接用旧库覆盖新成交。另一交易所和原运行路径保持独立。

**交付/门槛**：每个交易所单独通过启停恢复和订单对账；无孤儿挂单、重复订单、仓位失配或历史累计回退后再宣布切换完成。`grid-live-v1.0.0` 保留可追溯。

## 5. 验收清单与开发约束

| 维度 | 必须证明 |
| --- | --- |
| 决策一致性 | 相同标准事实和配置下，仿真与实盘路径的 Rule 意图及单元格状态一致；无格子在价格带等待时被较差位置永久挤占 |
| 订单安全 | 部分成交、手动取消、API 超时、重启和巡检不会造成重复开仓或漏补单；同一账户同一策略仅有一个写入调度器 |
| 财务一致性 | 净配对利润在逐笔手续费完整后确认；复投比例、最小增投单位和已消费金额准确；策略历史累计跨重配保留 |
| 迁移一致性 | 原策略 ID、运行起点、持仓归属与历史累计保留；新单元格统计从零开始；可预演、可复核、可回滚 |
| 接口隔离 | `trading_strategies` 不导入实盘或仿真实现；通用适配层没有 `grid` 专用命名；Binance/OKX 环境与数据库不串用 |

每一阶段单独提交可运行代码、测试和对应文档；不把所有目录一次性搬迁。改变交易行为前先用确定性回放证明等价。实盘迁移需要再次检查当时仓位与挂单状态，不能仅凭本计划自动执行。

## 6. 本分支第一轮工作

从 **S0 与 S1** 开始：先提交行为基线和依赖边界测试，再移动纯网格计算并消除反向依赖，同时让 Rule 使用实时单元格预算。完成后给出同一事实流的仿真/旧实盘意图差异报告，再进入共享运行契约设计。
