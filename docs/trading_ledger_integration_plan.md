# Strategy Trading 独立交易账本建设方案

## 1. 文档目的

本文用于规划 `strategy_trading` 仓库中的独立交易账本模块 `trading_ledger`。

`trading_ledger` 是一个可以单独安装、启动、测试和维护的应用，负责记录账户、交易、现金、持仓、持仓批次、参考价格和收益统计。当前阶段不与仓库中的其他业务模块交互，也不读取它们的数据库或运行时对象。

账本首期通过 Streamlit 提供人工操作页面，同时保留稳定的应用服务接口和版本化 HTTP API。未来自动交易系统产生真实成交后，由交易执行方调用账本 API 记账；账本只接受和核算成交事实，不负责生成策略信号、发送订单或控制交易执行。

---

## 2. 模块定位

### 2.1 当前定位

`trading_ledger` 当前是一个本地运行的人工交易账本，主要解决：

- 维护独立账户和初始资金；
- 在多个项目之间隔离账户、观察、交易、持仓和统计；
- 跟踪关注标的和当前持仓；
- 通过“来源”记录观察说明，通过“信号”记录买卖依据；
- 人工记录买入和卖出；
- 维护现金、持仓、成本和持仓批次；
- 保存参考价格及其来源；
- 查看交易历史、当前资产和阶段收益；
- 对错误记录进行可追溯冲正；
- 为未来外部交易系统提供统一记账 API。

### 2.2 独立运行边界

当前阶段遵循以下边界：

- 账本拥有独立 Python 依赖、SQLite 数据库、测试命令和启动入口；
- Streamlit 页面可以单独运行；阶段 4 完成后 API 服务也将独立运行；
- 不导入仓库内其他业务模块；
- 不访问其他模块的数据库、缓存或运行目录；
- 不要求其他模块配合才能启动；
- 不建立策略、实验或仿真结果关联；
- 不参与自动交易决策和订单执行。

同处一个仓库仅表示统一版本管理，不表示共享数据库、领域对象或运行进程。

### 2.3 未来 API 使用方式

```text
交易系统生成订单
→ 券商或交易所返回成交
→ 交易系统确认成交事实
→ 交易系统调用 trading_ledger API
→ 账本执行认证和幂等校验
→ 写入交易、现金流水和持仓批次
→ 返回记账结果
```

账本 API 不反向调用交易系统，也不因记账失败而自行补单、撤单或重试交易。

## 3. 建设目标与非目标

### 3.1 首期目标

- 建立统一、无开发阶段前缀的账本模型；
- 支持多个相互隔离的交易项目；
- 支持轻量的观察来源和买卖信号文字；
- 支持人工交易记录和持仓管理；
- 支持 A 股整手、现金和持仓校验；
- 支持交易确认、冲正和审计；
- 支持参考价格、资产估值和基础收益统计；
- 保证现金、交易、持仓和持仓批次相互守恒；
- 提供可独立运行的 Streamlit 页面；
- 定义并实现最小可用的 `/api/v1` 入站记账接口；
- 为未来自动交易调用保留稳定、可版本化的协议。

### 3.2 交易与说明可追溯目标

每笔正式交易至少能够回答：

1. 交易属于哪个项目和账户；
2. 标的、市场、方向、时间、价格和数量是什么；
3. 交易由人工录入还是外部系统写入；
4. 观察记录的来源以及本次买卖信号是什么；
5. 外部系统的成交编号和请求编号是什么；
6. 记账前后的现金与持仓如何变化；
7. 使用了哪些手续费和税费；
8. 由谁或哪个 API 客户端创建；
9. 是否发生过冲正，以及当前状态能否重新计算。

### 3.3 当前非目标

- 策略研究和参数优化；
- 市场仿真和撮合；
- 交易信号生成；
- 自动下单、撤单或订单状态机；
- 与仓库内其他模块的直接集成；
- 券商或交易所主动同步；
- 历史数据库导入和旧数据兼容；
- 多组织 SaaS、复杂审批流或统一门户；
- 复杂组合优化、VaR 或黑箱仓位模型；
- 对外审计、托管或清算能力。

## 4. 核心设计原则

### 4.1 单一正式账本

所有人工和 API 交易使用同一套业务表：

```text
projects
accounts
instruments
trade_records
cash_ledger
positions
position_lots
reference_prices
tracked_instruments
audit_events
```

人工录入与外部系统写入的区别通过 `execution_source`、`external_trade_id`、`request_id` 和操作者字段表达，不维护两套平行账本。

### 4.2 来源和信号保持轻量

当前没有固定的选股、审批或交易决策流程，因此首期只保存两个自由文字字段：

- “来源”就是观察说明，添加观察股时必填，后续可以编辑；
- “信号”就是本次交易依据，每笔人工或 API 买入、卖出均必填；
- 首期不建立独立 `decision_records`、审批状态、标签、目标仓位或决策关联；
- 来源和信号只承担说明与追溯作用，不自动触发交易；
- 后续流程稳定后再扩展结构化决策模型，不影响既有交易事实。

### 4.3 成交事实与订单执行分离

- 账本只记录已经确认的成交事实；
- 一个外部订单可以产生多笔成交；
- 每笔成交使用独立的外部成交编号；
- 未成交订单不进入交易账本；
- 订单被撤销不等同于冲正已成交记录；
- 外部订单状态由交易系统自身维护。

### 4.4 已确认记录不可直接修改

- 草稿可以取消；
- 已确认记录只能通过冲正纠错；
- 原记录、冲正记录和原因都必须保留；
- 冲正后重新计算现金、持仓和批次；
- 所有关键状态变化写入审计事件。

### 4.5 派生状态可以重算

`trade_records` 和 `cash_ledger` 是账本事实，`positions` 是查询优化用的派生状态。系统必须能够从有效交易和批次重新计算现金余额、持仓数量、可卖数量、平均成本以及已实现和未实现盈亏。

### 4.6 金额和时间必须精确

- 金额、价格、费用和税费在 Python 中使用 `Decimal`；
- API 中的小数使用字符串传输；
- SQLite 不依赖二进制浮点作为最终核算精度；
- 数量使用明确的整数或精度单位；
- 所有时间必须包含时区或使用统一 UTC 存储；
- 页面按配置的业务时区展示，默认 `Asia/Shanghai`。

### 4.7 查询不产生隐式写入

列表、统计和详情查询不得顺带修改业务状态。到期处理、估值刷新和状态重算必须由显式命令或定时任务触发。

### 4.8 前端先行，后端按确认后的流程落地

开发顺序采用前端先行，但阶段 0 不重新设计页面或搭建 Mock 系统。先完整保留现有 Streamlit + SQLite 页面和调用链，再逐项确认品牌、可见文案、配色、表单字段和项目切换方式，确认应用可以在 `trading_ledger` 中独立加载。

原型阶段遵循以下约束：

- 原代码文件按当前结构复制，不在阶段 0 重命名内部函数、服务或数据库表；
- 不新增非必要页面、Fake Service、领域抽象或 API 实现；
- 不导入历史数据库或业务数据；
- 只修改入口品牌、用户可见文案、深色主题配色和已经逐项确认的前端交互；
- 只做语法检查和页面能否加载的最小验证；
- 页面与流程确认后，再决定后续需要保留、删除或改造的功能。

前端先行用于发现真实使用流程，不降低后端阶段对事务、精度、幂等和账本守恒的要求。

### 4.9 项目是一等隔离边界

一个项目代表一套独立交易账本。每个项目独立维护账户资金、观察标的、来源、信号、交易、持仓、现金流水和统计结果；同一标的可以同时出现在多个项目中，但不得串用来源、信号、仓位或交易历史。

项目与账户的职责不同：项目是业务和数据隔离边界，账户是项目内的资金核算主体。首期界面按“一个项目对应一个主账户”实现，数据模型保留以后扩展多个账户的能力。

以下数据可以跨项目共享：

- 标的基础信息；
- 市场行情和参考价格；
- 市场交易单位、结算和费税规则。

以下数据必须包含或能够严格归属到 `project_id`：

- 账户及资金流水；
- 当前跟踪、来源和观察状态；
- 来源和买卖信号；
- 交易、持仓和持仓批次；
- 审计事件、幂等记录和统计结果。

项目使用不可变、唯一的 `project_key` 作为页面链接和 API 标识，使用可修改的 `project_name` 作为显示名称。已有账本记录的项目不提供物理删除，只允许归档。

## 5. 目标目录结构

```text
strategy_trading/
└── trading_ledger/
    ├── README.md
    ├── pyproject.toml
    ├── app.py
    ├── migrations/
    ├── scripts/
    ├── src/
    │   └── trading_ledger/
    │       ├── domain/
    │       ├── application/
    │       ├── infrastructure/
    │       ├── api/
    │       └── web/
    └── tests/
        ├── unit/
        ├── integration/
        └── api/
```

| 目录 | 职责 |
| --- | --- |
| `domain` | 账户、交易、现金、持仓、批次和冲正规则 |
| `application` | 用例服务、事务边界、幂等控制和查询服务 |
| `infrastructure` | SQLite、Schema 版本、仓储、行情适配和配置 |
| `api` | FastAPI 路由、请求模型、认证和错误映射 |
| `web` | Streamlit 页面和展示模型 |
| `migrations` | 新账本数据库的版本化 Schema 变更 |
| `scripts` | 初始化、备份、恢复、校验和重算工具 |
| `tests` | 单元、数据库集成、API 合约和页面测试 |

Streamlit 和 FastAPI 共同调用 `application` 服务，不在页面或路由中直接写 SQL。

## 6. 运行形态

### 6.1 本地人工账本

```text
Streamlit
→ Application Service
→ Domain Rules
→ Repository
→ 独立 SQLite
```

### 6.2 外部 API 记账

```text
交易执行方
→ FastAPI /api/v1
→ 认证与幂等校验
→ Application Service
→ Domain Rules
→ Repository
→ 独立 SQLite
```

两种入口共享完全相同的业务规则和事务实现。

### 6.3 启动入口

- `streamlit run app.py`：启动人工操作页面；
- `trading-ledger-api`：阶段 4 计划提供的记账 API 启动入口，当前尚未实现。

默认 API 只绑定 `127.0.0.1`。需要被其他主机访问时，必须显式配置监听地址、认证和网络访问控制。

## 7. 核心数据模型

### 7.0 项目 `projects`

| 字段 | 含义 |
| --- | --- |
| `project_id` | 内部主键 |
| `project_key` | 不可变、唯一，供页面链接和 API 使用 |
| `project_name` | 可修改的显示名称 |
| `description` | 可选说明 |
| `status` | 活跃、归档 |
| `created_at` | 创建时间 |
| `archived_at` | 归档时间，可空 |

项目创建时必须同时创建主账户和初始资金流水，任一步失败都整体回滚。项目名称在所有活跃和归档项目中不区分大小写唯一；名称和说明可以修改，初始资金在创建后不可直接修改，后续资金变化只能通过资金流水完成；`project_key` 不随名称变化。已有账本事实的项目只允许归档，不物理删除，并且至少保留一个活跃项目。

### 7.1 账户 `accounts`

| 字段 | 含义 |
| --- | --- |
| `account_id` | 内部主键 |
| `project_id` | 所属项目 |
| `account_code` | 对人工和 API 稳定的唯一账户编码 |
| `account_name` | 显示名称 |
| `account_type` | `MANUAL`、`ACTUAL` 等 |
| `market` | A 股、美股、加密等 |
| `base_currency` | CNY、USD、USDT、BTC 等 |
| `initial_capital` | 初始资金 |
| `cash_balance` | 当前现金派生值 |
| `status` | 活跃、冻结、归档 |
| `opened_at` | 启用时间 |
| `created_at` | 创建时间 |

首期每个项目只有一个活跃主账户；`account_code` 在项目内唯一。后续增加多账户时，账户之间仍不得共享现金、持仓或批次。

### 7.2 标的 `instruments`

标的身份不能只依赖显示代码，唯一性至少由市场、交易场所和代码共同确定。

| 字段 | 含义 |
| --- | --- |
| `instrument_id` | 主键 |
| `market` | 市场 |
| `venue` | 交易场所 |
| `symbol` | 标准代码 |
| `name` | 名称 |
| `currency` | 计价币种 |
| `quantity_precision` | 数量精度 |
| `price_precision` | 价格精度 |
| `lot_size` | 整手数量 |
| `t_plus_days` | 可卖延迟规则 |
| `status` | 活跃、停用 |

### 7.3 交易记录 `trade_records`

| 字段 | 含义 |
| --- | --- |
| `trade_id` | 内部主键 |
| `project_id` | 所属项目 |
| `account_id` | 账户 |
| `instrument_id` | 标的 |
| `signal_text` | 必填，本次买入或卖出的信号说明 |
| `side` | `BUY`、`SELL` |
| `trade_time` | 成交时间 |
| `quantity` | 成交数量 |
| `price` | 成交价格 |
| `gross_amount` | 成交金额 |
| `commission_amount` | 手续费 |
| `stamp_tax_amount` | 印花税 |
| `transfer_fee_amount` | 过户费 |
| `net_cash_amount` | 含全部费税后的实际资金变化 |
| `execution_source` | `MANUAL`、`AUTO_TRADING`、`IMPORT` |
| `record_status` | `DRAFT`、`CONFIRMED`、`REVERSED` |
| `external_trade_id` | 外部成交编号，可空 |
| `request_id` | API 请求幂等编号，可空 |
| `reversal_of_trade_id` | 被冲正交易，可空 |
| `metadata_json` | 非核算扩展信息 |
| `created_by` | 人工操作者或 API 客户端 |
| `created_at` | 录入时间 |

约束：

- `account_id` 必须属于同一个项目；
- `(execution_source, external_trade_id)` 在外部编号非空时对整个账本唯一，禁止换项目重复提交同一成交；
- `(project_id, request_id)` 在 API 调用中唯一；
- 同一幂等键重复提交相同内容时返回原结果；
- 同一幂等键提交不同内容时返回冲突，不得覆盖原记录。

### 7.4 现金流水 `cash_ledger`

| 字段 | 含义 |
| --- | --- |
| `cash_entry_id` | 主键 |
| `account_id` | 账户 |
| `trade_id` | 关联交易，可空 |
| `entry_type` | 初始资金、入金、出金、买入、卖出、费用、税费、冲正 |
| `currency` | 币种 |
| `amount` | 带符号金额 |
| `balance_after` | 该流水后的现金 |
| `occurred_at` | 发生时间 |
| `reversal_of_entry_id` | 被冲正流水，可空 |
| `created_at` | 创建时间 |

### 7.5 当前持仓 `positions`

`positions` 是派生表，不是不可替代的原始事实。

| 字段 | 含义 |
| --- | --- |
| `account_id` | 账户 |
| `instrument_id` | 标的 |
| `quantity` | 当前数量 |
| `available_quantity` | 当前可卖数量 |
| `average_cost` | 平均成本 |
| `realized_pnl` | 累计已实现盈亏 |
| `last_price` | 最近参考价 |
| `market_value` | 市值 |
| `unrealized_pnl` | 未实现盈亏 |
| `updated_at` | 更新时间 |

### 7.6 持仓批次 `position_lots`

- 买入生成新批次；
- 批次保存来源交易、单位成本、剩余数量和可卖日期；
- 卖出按 FIFO 消耗可卖批次；
- 批次数量合计必须等于持仓数量；
- 冲正后按有效交易重新构建受影响批次。

### 7.7 参考价格 `reference_prices`

参考价格保存标的、价格、行情时间、采集时间、来源、是否手工输入以及原始来源摘要。它只用于预览、估值和收益统计，不自动变成成交价格。

### 7.8 当前跟踪 `tracked_instruments`

每条当前跟踪记录必须属于一个项目。同一标的可以出现在不同项目中，但同一项目内只能有一条当前有效记录。

| 字段 | 含义 |
| --- | --- |
| `tracking_id` | 主键 |
| `project_id` | 所属项目 |
| `instrument_id` | 标的 |
| `source_text` | 来源，即观察说明；添加和编辑观察股时必填 |
| `tracking_status` | 观察中、持仓中、已关闭、已过期、已归档 |
| `added_at` | 加入时间 |
| `expires_at` | 观察失效时间，可空 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

观察到期由显式任务处理，不允许列表查询顺带修改状态。操作历史中，观察记录显示 `source_text`，交易记录显示 `signal_text`。

### 7.9 审计事件 `audit_events`

审计事件必须记录所属项目，并保存对象、动作、操作者或 API 客户端、请求 ID、变更前后摘要、原因和时间。审计内容不得保存 API 密钥、Authorization 头或其他凭证。

## 8. 账本业务规则

### 8.1 买入

- 人工页面接受用户自由填写的可用资金百分比，范围为 `0 < ratio <= 100%`，不使用固定比例选项；
- 买入预算等于当前可用资金乘以填写比例，成交金额与手续费合计不得超过该预算；
- A 股默认按 100 股向下取整，预算不足一手时拒绝确认；
- 现金必须覆盖成交金额、手续费和税费；
- 确认后原子写入交易、现金流水、持仓和批次；
- API 提交必须通过幂等校验。

### 8.2 卖出

- 人工页面接受用户自由填写的可卖持仓百分比，范围为 `0 < ratio <= 100%`，不使用固定比例选项；
- 卖出数量不得超过可卖批次数量；
- 交易账本不限制同日买卖，买入后持仓立即可用于卖出记账；
- 部分卖出按 FIFO 批次核算成本；
- 非清仓卖出按 100 股向下取整；
- 100% 清仓时允许处理合法零股尾差；
- 确认后原子写入交易、现金流水和持仓变化。

### 8.3 手续费和税费

- 买入和卖出手续费均为成交额的万分之 `0.85`，每笔最低 `5.00 CNY`；
- 买入不收取印花税和过户费；
- 卖出印花税为成交额的 `0.1%`；
- 卖出过户费为成交额的十万分之一；
- 每项费用分别使用 `Decimal` 按人民币分计算和保存，舍入方式统一为 `ROUND_HALF_UP`；
- 买入现金减少额为成交金额加手续费，卖出现金增加额为成交金额减手续费、印花税和过户费。

### 8.4 入金与出金

- 入金和出金必须生成独立现金流水；
- 出金不得使现金余额小于零；
- 外部资金流不计入投资收益；
- 冲正资金流时保留原流水。

### 8.5 冲正

- 只能冲正已确认记录；
- 同一记录不得重复有效冲正；
- 冲正必须填写原因和操作者；
- 原记录继续可查询；
- 现金、持仓、批次和收益同步重算；
- 冲正操作保存为独立审计事件。

### 8.6 事务与并发

```text
校验账户和标的
→ 校验幂等键
→ 校验现金或可卖数量
→ 写入交易
→ 写入现金流水
→ 更新或重算持仓批次
→ 更新持仓派生值
→ 写入审计事件
→ 提交事务
```

任一步失败都必须整体回滚。SQLite 应配置合理的 busy timeout，并对同账户写入建立明确的串行化策略。

## 9. Streamlit 页面

### 9.1 已确认的前端合同

侧边栏只保留品牌区和功能导航，不单独放置“当前项目”区域。项目管理页面以列表提供项目切换和维护入口；除项目管理外，其他页面均在大标题后显示当前项目名称。切换项目后，所有页面统一使用新的 `project_id` 重新查询，不允许各页面自行创建或选择默认项目。

## 10. 入站记账 API

### 10.1 API 原则

- 路径从 `/api/v1` 开始版本化；
- 请求和响应使用稳定的 JSON Schema；
- 除健康检查和共享参考价格外，所有账本请求必须通过路径明确提供 `project_key`；
- 所有写请求必须提供 `request_id`；
- 自动交易成交必须提供 `external_trade_id`；
- 买入和卖出必须提供非空 `signal_text`；
- 数量、价格、费用和税费使用十进制字符串；
- API 调用与人工页面使用相同的应用服务；
- API 不暴露数据库表结构；
- API 不提供下单、撤单或策略控制能力；
- 日志和错误响应不得包含凭证。

### 10.2 最小端点

| 方法与路径 | 用途 |
| --- | --- |
| `GET /api/v1/health` | 健康状态和只读版本信息 |
| `POST /api/v1/projects/{project_key}/trades` | 记录一笔已确认成交 |
| `GET /api/v1/projects/{project_key}/trades/{trade_id}` | 查询记账结果 |
| `POST /api/v1/projects/{project_key}/trades/{trade_id}/reversals` | 冲正已确认交易 |
| `POST /api/v1/projects/{project_key}/cash-entries` | 记录入金或出金 |
| `GET /api/v1/projects/{project_key}/accounts/{account_code}` | 查询账户摘要 |
| `GET /api/v1/projects/{project_key}/accounts/{account_code}/positions` | 查询当前持仓 |
| `POST /api/v1/reference-prices` | 写入外部参考价格，可选 |

### 10.3 成交记账请求示例

调用路径示例：`POST /api/v1/projects/long-term-a/trades`。项目由路径中的 `project_key` 唯一确定，请求体不接受或推断另一个默认项目。

```json
{
  "request_id": "01JEXAMPLE9K1A2B3C4D5E6F7G8",
  "source": "AUTO_TRADING",
  "external_trade_id": "exchange-fill-20260902-0001",
  "account_code": "primary-cny",
  "market": "CN_STOCK",
  "venue": "SSE",
  "symbol": "600000.SH",
  "side": "BUY",
  "trade_time": "2026-09-02T10:15:30+08:00",
  "quantity": "100",
  "price": "12.34",
  "signal_text": "突破前期平台",
  "commission_amount": "5.00",
  "stamp_tax_amount": "0.00",
  "transfer_fee_amount": "0.00",
  "metadata": {
    "external_order_id": "order-20260902-001"
  }
}
```

人工页面不提交费用计算结果，由应用服务根据统一费率计算。API 记录真实成交时可以提交券商确认的费用明细；未提供时由应用服务按同一费率补算。API 提交的费用不得为负数，并必须与买卖方向允许的费用类型一致。

### 10.4 幂等和错误响应

- 首次成功写入：`201 Created`；
- 相同幂等键和相同内容重复提交：`200 OK`，返回原 `trade_id`；
- 相同幂等键但内容不同：`409 Conflict`；
- 现金或可卖数量不足：`422 Unprocessable Entity`；
- 账户被冻结或不存在：`404` 或 `409`；
- 未通过认证：`401 Unauthorized`。

交易系统可以在同一项目内安全重试超时请求，但不得通过生成新 `request_id` 绕过幂等检查。同一个外部成交不得提交到多个项目；检测到项目与授权范围或账户归属不一致时必须拒绝。

### 10.5 认证与部署预留

首期至少支持配置化 Bearer Token，并预留 API Client ID、Token 轮换、请求时间戳和重放保护、HMAC 或 mTLS、IP 白名单及调用频率限制。

凭证只从环境变量或受控密钥存储读取，不进入 SQLite、审计事件、异常文本或请求日志。

## 11. 数据库初始化与版本管理

### 11.1 全新数据库

账本从空数据库开始，不读取、导入或兼容任何历史数据库。初始化只创建当前模块需要的表、索引和默认配置。

可提供两种初始化模式：

- 空白模式：只创建 Schema，由用户建立账户和标的；
- 演示模式：写入明确标记为演示的虚构账户和交易。

演示数据不得默认进入正式数据库。

### 11.2 Schema 版本

虽然不做历史数据导入，仍需要版本化 Schema 变更，以支持 `trading_ledger` 自身后续升级：

- 每个版本只执行一次；
- 升级前自动备份；
- 重复运行无副作用；
- 失败时事务回滚；
- 应用启动前检查数据库身份和兼容版本；
- 不允许把其他 SQLite 文件误识别为账本数据库。

### 11.3 备份与恢复

- 支持 SQLite 在线备份；
- 备份文件默认写入忽略目录；
- 恢复前校验数据库身份和完整性；
- 恢复后执行现金、持仓和批次守恒检查；
- 不自动覆盖现有数据库。

当前正式导航为当前跟踪、操作历史、交易统计和项目管理。项目、来源和信号均已持久化；项目选择写入 URL；行情刷新和每日估值支持用户显式触发及独立定时任务，观察到期仍由显式命令触发。旧 `paper_*`、`theory_*` 和原型服务代码已从模块移除。

## 16. 最终边界

`trading_ledger` 是仓库中的独立账本应用：

- 当前由人工页面维护项目、账户和交易；
- 支持多项目，每个项目的账户、观察、来源、信号、交易、持仓、流水和统计严格隔离；
- 标的基础信息、行情和市场规则可以跨项目共享；
- 使用自己的依赖、配置、数据库和测试；
- 当前不与仓库内其他业务模块交互；
- 不处理任何历史数据库导入；
- 不生成信号、不撮合、不下单；
- 未来由交易执行方通过带有 `project_key` 的 `/api/v1/projects/{project_key}` 路径提交已确认成交；
- 人工录入和 API 写入共享同一套账本规则；
- 所有写入必须可追溯、可幂等、可冲正和可复算。
