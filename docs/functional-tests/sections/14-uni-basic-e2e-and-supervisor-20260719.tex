\subsection{执行中发现的双调度器缺陷}

首次启动 UNI 时，平台存在四张有效订单，但最低 Cell 在同一秒先记录 \texttt{ENTRY\_PLACED}，随后被另一轮处理记录为 \texttt{ENTRY\_MISSING} 并进入 \texttt{manual\_review}。检查发现测试数据库同时被 PID 59072 与 PID 6512 两个调度器轮询。

旧进程从不同工作目录启动，命令中的相对 \path{runtime/scheduler.pid} 实际解析为下列路径：

\begin{quote}
  \small\path{runtime/overnight-testnet-20260718/runtime/scheduler.pid}
\end{quote}

API 在项目根目录查找 \path{runtime/scheduler.pid}，没有发现旧 PID，因而错误启动第二个调度器。两个进程共享 SQLite，但各自持有不同订单快照，造成刚下发订单被另一个进程短暂判为不存在。

本轮立即停止新 PID 6512，保留原 PID 59072。页面执行 UNI 停止和重启后，唯一调度器按四个 \texttt{clientOrderId} 产生四条 \texttt{OPEN\_ORDER\_RECOVERED}，最低 Cell 从人工检查恢复为待建仓；平台订单总数始终为四张，没有重复补单。

代码修复将 SQLite 路径、日志目录和 PID 文件在对象构造时统一解析为绝对路径，子进程参数也只传绝对路径。新增 \path{test_scheduler_paths_do_not_change_with_working_directory}，验证创建 Store/Supervisor 后即使进程工作目录变化，数据库和 PID 文件仍指向同一绝对位置。

本轮结论：\StatusPass。页面基本业务链路和订单恢复链路通过；同时发现并修复了一个可能导致重复共享调度器的高风险进程管理缺陷。部署新代码时必须在安全窗口重启 FastAPI 与共享调度器，使绝对路径修复在长期运行进程中生效。
